# 战国绘卷（Sengoku Scroll）

《战国绘卷》是一个以日本战国时代为背景的暂停式大战略游戏原型。当前主线已经形成可运行闭环：剧本开局、内政、税收、市场贸易、外交、谍报、角色行为、行军、野战、攻城、占领、和谈、胜负判定、存档读档、全势力 AI 观战，以及 1–8 人服务器权威房间联机。

本文面向开发、测试和维护人员。玩家请阅读 [MANUAL.md](MANUAL.md)。

## 项目状态

| 项目 | 当前状态 |
| --- | --- |
| 游戏模式 | 单机大战略、全势力 AI 观战、1–8 人局域网房间联机 |
| 内置剧本 | `mini_kanto` |
| 后端 | .NET 10 / ASP.NET Core |
| 前端 | Vue 3 / TypeScript / Vite / PixiJS / ECharts / Element Plus |
| 自动化测试 | 480 项 .NET 测试 + 11 项前端回归测试（2026-09-05 内存优化验收） |
| 存档 | V2 完整世界与运行时服务状态；10 个本地槽位；兼容旧存档 |
| 确定性 | 固定种子、稳定哈希、并行有序输出、双局 365 日存档一致性测试 |
| 发行方式 | Windows `win-x64` 自包含单文件包 |

当前版本适合原型试玩、规则验证、AI 长稳测试和继续开发，不应被误解为已经完成商业内容制作。RPG、独立战术地图、MMO、多剧本、完整事件链、完整建设与婚姻系统仍属于后续立项范围。

| `scripts` | 辅助诊断和开发脚本 |

依赖方向以领域层为核心：Web 前端调用 API，API 进入单局仿真宿主，宿主执行领域动作或按日推进系统链，再把只读世界状态映射成 DTO 返回前端。前端不自行复制权威游戏规则。

```text
Vue / PixiJS / ECharts
          │ HTTP + JSON
          ▼
ASP.NET Core Controller / SignalR Hub
          ▼
单机 StrategySimulationHost 或 RoomManager → 每房间独立 Host
          ▼
Strategy Game Engine（按 Order 日结）
          ▼
Domain + Strategy Rules / Systems / Ledgers
```

## 一日仿真顺序

系统由 `IGameSystem.Order` 排序执行；同一顺序保持注册次序。主要阶段如下：

| Order | 系统 | 主要职责 |
| ---: | --- | --- |
| 0 | `StrategyTimeSystem` | 日期、季节与时间推进 |
| 1 | `ClimateSystem` | 气候阶段接口；当前仍是轻量实现 |
| 6 | `StrategyReserveCommanderSystem` | 预备队与指挥关系维护 |
| 8 | `StrategyMarketSystem` | 市场刷新、订单与价格处理 |
| 10 | `StrategyEconomySystem` | 税收、产出、势力经济结算 |
| 14 | `StrategyMigrantSystem` | 流民运输队推进与到达 |
| 15 | `StrategySupplySystem`、`StrategyStrongholdGovernanceSystem` | 补给与据点治理 |
| 16 | `StrategyRecruitTaskSystem` | 征兵任务结算 |
| 17 | `StrategyCharacterAISystem` | 人物级 AI 行为 |
| 18 | `StrategyAISystem` | 势力军事与经济决策 |
| 19 | `StrategyDiplomacyMissionSystem` | 外交使节与任务结算 |
| 20 | `StrategyUnitSystem` | 部队移动和行动点恢复 |
| 21–23 | 攻城、接战、占领系统 | 战场生成、攻城推进、据点归属变化 |
| 25 | 视野与信使系统 | 战争迷雾、情报可见性和消息送达 |
| 26 | `StrategyBattleResolutionSystem` | 野战结算、战报与战果 |
| 30–32 | 人物、体力、长期目标系统 | 人物成长、恢复和目标刷新 |

这个顺序具有规则语义。例如，移动后产生接战，战斗和占领再影响下一阶段的视野与消息；不能为了并行而任意交换。

## Web API 概览

API 同时挂载在 `/strategy` 和 `/api/strategy`。主要端点分组如下：

- 世界：加载剧本、读取世界状态、读取地图、推进一天或多天。
- 部队：路径预览、移动、攻击、攻城、方针、部署、入城、出城、合并、分割、解散。
- 人物：移动、进出据点、交谈、赠礼、招募、任命、调动和召回。
- 据点：税率、治理优先级、征兵、雇佣兵、市场和商品交易。
- 外交：关系调整、同盟、宣战、臣属、内藩、使节任务、和谈预览与执行。
- 情报：谍报登记以及按观察势力过滤的世界 DTO。
- 存档：即时导出/恢复和 1–10 号本地存档槽。
- 诊断：移动轨迹、AI 决策轨迹和日结日志。
- 多人：房间列表、创建/加入/退出、势力占用、重连、准备推进和 SignalR 房间通知。

所有会改变世界的入口经 `StrategySimulationHost` 的单局锁串行化，避免 HTTP 命令和自动日推进同时写入世界。

联机状态下，客户端继续调用同一组 `/api/strategy/*` 指令，但必须携带房间号、玩家令牌和写命令唯一 ID。服务端在房间门锁内切换到该玩家势力，完成所有权校验、规则执行和按势力裁剪的 DTO 映射。直接加载剧本、直接推进日期、即时战斗和单机存档接口会被拒绝。详见 [多人联机 MVP](docs/multiplayer-mvp.md)。

## 多核优化

### 设计原则

策略仿真采用“并行只读计算、固定顺序提交”。会写兵力、金粮、据点归属、战争分数或实体集合的步骤仍串行执行；只读且相互独立的重计算可以并行。这样既使用多核，也保持同一种子和同一命令序列的结果可复现。

统一调度入口为 `StrategyParallelWork`：

- 单个并行区域最大并行度默认为 `Environment.ProcessorCount - 1`，最少 1；可用进程环境变量 `SENGOKU_MAX_PARALLELISM` 调低，重启生效。这不代表操作系统会保留一个核心。
- 同一进程只允许一个计算区域展开并行；其他房间与嵌套计算继续顺序执行，避免各自重复申请整机并行度。
- 按每个工作线程的最小批量分配并行度；不足两个批次的集合走顺序路径，避免小任务展开整机线程预算。
- `MapOrdered` 按输入索引写入结果；任务完成顺序不会改变输出顺序。
- 并行阶段禁止直接修改共享世界，计算结果回到稳定顺序后再提交。

### 已并行或批处理优化的热点

- 各势力视野快照独立计算，每个工作线程至少分配 4 个势力，至少 8 个势力才尝试并行。
- AI 的敌军/敌城感知按势力并行预计算；具体决策与行动仍按势力 ID 提交。
- 势力、据点、单位、人物和地图人物的世界 DTO 大集合并行映射。
- 地形与区域数组每个工作线程至少分配 4096 格，至少 8192 格才尝试并行转换。
- 人物长期目标先一次聚合领地统计，再并行刷新大批人物。
- 高速观战批量推进多日，只在批次末映射和序列化一次完整状态。

### 明确保留串行的区域

- 具有先后因果的一日系统链。
- 战斗伤亡、占领、商队撮合、税费、贡纳和实体增删。
- 同一局中的玩家命令、存档、读档和日期推进。

不要把 `Parallel.ForEach` 直接包在系统链外层。继续优化战斗时，应先建立参战单位冲突图，只并行完全不共享参战者的战场计算，再按战场 ID 顺序应用结果；经济系统同理，应先生成每城增量命令，再顺序提交。详见 [多核优化说明](docs/multicore-optimization.md)。

## 确定性与随机数

- 世界保存 `SimulationSeed`，关键随机过程从稳定种子派生。
- `DeterministicHash` 替换了跨进程不稳定的运行时字符串哈希。
- 不使用 `Random.Shared` 驱动权威世界结果。
- 集合在映射、AI 提交和存档前按稳定 ID 排序。
- `StrategyParallelWorkTests` 用 10,000 项验证有序并行映射。
- 两局全势力 AI 使用相同种子各推进 365 日，最终存档 JSON 必须逐字一致。

任何新并行代码都必须通过确定性回归；“没有抛异常”不等于结果可复现。

## 存档与运行时状态

V2 存档不仅保存实体，还保存会影响未来结果的运行时服务状态，包括视野、谍报、市场、税费、贡纳、战场、占领、待送达事件和战争分数等。读档时会：

1. 重建世界实体和引用关系；
2. 恢复运行时台账与等待队列；
3. 丢弃失效引用，避免复活已销毁部队或过期任务；
4. 重新计算需要派生的可见性；
5. 保持对旧版存档缺省字段的兼容。

单机存档默认写入程序旁的 `App_Data`，提供 10 个槽位。`Maps` 和 `App_Data` 应纳入备份。多人房间默认自动保存至 `App_Data/multiplayer-rooms`，重启恢复世界、访客凭据、回合、去重和私人消息；仍禁用单机存档槽。目录含私密凭据，不得公开。配置与异常恢复见 [多人运维说明](docs/multiplayer-mvp.md)。

## 已修复的主要问题

最新一轮：私人消息、房间快照恢复、AI 最后侦察记录，以及税赋溢出、溃败递归崩溃和技能存档遗漏修复。见 [多人可靠性更新](docs/multiplayer-reliability-2026-09-05.md)。

### 规则与稳定性

- 修复部队穿越据点、行动点消耗、堆叠、撤退、解散和运输队行为的边界错误。
- 修复攻城、占领、战斗报告、战后逃离以及战争结束后的残留关系。
- 增加战争分数事件、和谈条款预览与结算，避免战争只能开始不能合理结束。
- 完善税收、市场刷新、商品交易、贸易税、贡纳、流民和补给闭环。
- 修复存档遗漏运行时台账、动态销毁实体和等待事件导致的读档分叉。
- 修复人物驻城/出城、体力、任务、领主继承、交谈、赠礼和长期目标的状态冲突。

### AI 与情报公平性

- 军事进攻目标使用可见敌军与敌城最后侦察记录，隐藏城池实时增兵/易主不再直接改变 AI 目标评分；援防目标过滤未观察到的威胁。尚不宣称所有军事/外交决策已实现统一情报时延。
- 经济 AI 根据现金、粮食、兵力、风险和已知市场信息行动，不再盲目刷交易。
- 外交 AI 能基于战分、国力和持续时间评估和谈。
- 谍报按观察势力隔离并带有效期，避免一方获得的情报泄漏给所有势力。
- 全势力 AI 观战明确使用观察者全图视角，不污染普通玩家的迷雾规则。

### 前端与交互

- 主界面接入真实 API，移除生产路径中的 Mock 依赖。
- 补齐新局难度、观战、教程、胜负状态、角色互动、外交和谈和存档槽界面。
- 大型依赖按需拆包，减少首屏包体压力。
- 修正已落地功能仍显示“尚未实装”的陈旧提示；未落地按钮则明确给出原因。
- 锁定存在已知安全修复的前端传递依赖版本。

## 设计冲突的处理

| 冲突 | 当前统一规则 |
| --- | --- |
| 玩家直接控制 vs 当主委任 | 简易可直接控制；标准/困难采用方针或角色指挥，受命令所有权校验 |
| 战争迷雾 vs 完整数值面板 | 世界 DTO 按观察势力裁剪；未知目标只显示已掌握或过期前最后情报 |
| 即时 UI 反馈 vs 传令时间 | 操作结果即时确认；战报和远方事件可由信使延迟送达 |
| 角色行动 vs 势力行动 | 人物任务消耗个人体力并受所在位置约束；势力命令受控制模式约束 |
| 多核吞吐 vs 可复现存档 | 并行计算只读快照，所有世界修改固定顺序提交 |
| 原型设计文档 vs 已实现范围 | 玩家手册只把可操作闭环当成正式功能；远期设计明确标记为未落地 |

## 本地开发

需要：

- .NET 10 SDK
- Node.js 20 或更新版本
- npm（仓库同时保留 pnpm 锁文件）

Windows 可双击 `dev.cmd`。手动启动方式：

```powershell
dotnet run --project .\SengokuScroll.WebApi\SengokuScroll.WebApi.csproj --launch-profile http
```

另开终端：

```powershell
cd .\SengokuScroll.WebClient
npm ci
npm run dev
```

- 前端开发地址：`http://localhost:5173/`
- API 与 Swagger：`http://localhost:5100/swagger`

局域网联机开发可使用：

```powershell
dotnet run --project .\SengokuScroll.WebApi\SengokuScroll.WebApi.csproj --launch-profile lan
```

开发时还需启动前端 `npm run dev`，其他设备访问 `http://主机局域网IP:5173/`，由 Vite 转发 API。`lan` 配置使用 Development，5100 端口只提供后端；发行包才在 5100 同时提供网页。不要在没有 TLS、正式账号和限流的情况下把当前 MVP 直接暴露到公网。

## Windows 发行包

运行：

```powershell
.\build.cmd
```

脚本会构建前端，将静态资源嵌入 ASP.NET Core，并发布 `win-x64` 自包含单文件版本：

```text
build/release-<随机编号>/
├─ SengokuScrollGame.exe
├─ LaunchGame.cmd
└─ README.txt
```

每次打包创建新目录，保留旧发行版和存档，不强制结束运行中的游戏。前端直接从 `dist` 嵌入，不删除开发目录中的 `wwwroot`。运行后访问 `http://127.0.0.1:5100/`；`Maps` 由发布复制，`App_Data` 存档需自行备份并迁移到新发行目录。`build/`、存档和本机日志不得提交到 Git。

## 已知限制与后续路线

- 当前只有小型 `mini_kanto` 剧本，规模不足以代表大型地图的最终性能。
- 气候、建设队列、手动据点运输、运输改道、完整婚姻/派系/事件系统仍未完成。
- RPG、战术地图和 MMO 文档属于远期设计，尚未接入可玩主线。
- 美术仍以原型资源为主，需要统一角色、建筑、单位和 UI 资产管线。
- 多人 MVP 已实现独立宿主、命令门锁、按势力信箱与本地快照重启恢复；尚无数据库事务日志、正式账号、TLS、限流和多节点路由，不应直接公开部署。
- 大型剧本落地后应重新采集 CPU profile、GC、JSON 和前端绘制数据，再决定下一轮并行重点。
- 仓库未见明确许可证文件；公开分发或接受外部贡献前，所有者应补充许可证与资产授权说明。
