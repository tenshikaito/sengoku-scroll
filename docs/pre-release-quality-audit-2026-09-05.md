# 发布前独立质量复核 — 2026-09-05 20:46

后续状态：下列四项已修复并完成回归验收，见 [修复验收记录](release-quality-fixes-2026-09-05.md)。以下保留当时的审计证据，不代表修复后的当前结论。

结论：现有主循环、正常存档/重启路径和多世界并发具备测试基础，但发现 3 项发布前应修的 P1 缺陷、1 项 P2 确定性问题。不建议现在冻结对外交付版本。本轮仅审计与隔离复现，未修改业务逻辑、推送 Git 或打标签。

## 已复现的发现

### P1：损坏的 v2 多人世界会静默降级恢复

位置：`SengokuScroll.Strategy/Persistence/StrategyWorldSaveService.cs:392`。

v2 `RuntimeState` 解析失败后，`Apply` 继续走旧版逐字段恢复，而不是拒绝损坏的新格式世界。隔离实验：正常多人存档的 `runtimeState.Units` 改为 null，外层 JSON 仍合法，`RestoreSave` 返回成功。旧字段只覆盖部分状态，不能代表完整运行时世界；这可能把剧本初始实体与存档中的台账、命令、信箱拼在一起。房间启动也不能将它按坏快照隔离。

建议：区分“确为旧版无完整世界”与“新版完整世界损坏”。后者严格拒绝，保留当前世界/磁盘快照，并增加单机、多人和启动恢复反例测试。

### P1：当主继位后，部分查询仍引用旧当主

位置：`SengokuScroll.Strategy/Helpers/StrategyStrongholdLordHelper.cs:27`；关联 `Rules/ForceSuccessionRules.cs:129`。

继承更新运行时注册表与 `Force.LordCharacterId`；不带注册表的公共解析函数却直接回退剧本元数据，忽略运行时当主。真实继承规则的隔离调用结果：旧当主 1 阵亡、角色 2 成功继位；带注册表查询为 2，但视野和战报调用使用的不带注册表查询仍为 1。可能让角色视野、信使收件位置、称谓和当主权限继续围绕旧角色工作。

建议：统一运行时当主权威来源，校验存活/归属，并覆盖继承后观察、下令、战报与读档测试。

### P1：战报寻路失败仍投递完整战斗数据

位置：`SengokuScroll.Strategy/Helpers/BattleReportDeliveryHelper.cs:135`、`:188`。

当派遣信使返回 null 时，直接调用失败通知；该通知依然包含原始 `BattleResult`，并登记为已通知。隔离实验使用正常多人标准难度、`InstantEventMessages=false`、返回无路径的寻路实现；结果是“道路不通”的失败提醒同时携带完整战报。战略报告失败分支也附带原始详细内容。

建议：失败提醒与成功投递的载荷、去重状态分离；失败不能解锁完整远方情报，也不应妨碍以后成功收件。增加断路、重试、恢复和重复目的地测试。

### P2：读档续玩后的消息顺序不完全确定

位置：`SengokuScroll.Strategy/Helpers/SupplyConvoyDispatchHelper.cs:342` 与 `Rules/TransportUnitRules.cs:57`；部分台账快照亦未固定排序。

实验比较连续 60 日与“30 日→JSON 存档恢复→30 日”。单机、多人的世界实体值语义一致；但序列化顺序和部分台账数组顺序不同。多人势力 1 的两份信箱均有 62 条，事件内容相同，但第 47 条分别是不同贸易队到账消息，序号/顺序出现分叉。运输队遍历依赖可变字典内部顺序，恢复后该顺序未必保留。

建议：对影响输出、事件序号和世界写入的遍历按稳定实体 ID 排序；台账快照采用明确排序。增加跨存档检查点的长期一致性测试，而不只测试两个从头运行的世界。
