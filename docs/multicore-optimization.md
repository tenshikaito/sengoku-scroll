# 多核优化说明

## 原则

策略仿真采用“并行只读计算、固定顺序提交”。并行阶段不能写共享世界；涉及兵力、金粮、据点归属、战争分数和实体增删的结果必须按系统 Order、势力 ID、实体 ID 顺序提交。这样才能保证相同种子、相同命令得到相同存档。

统一调度入口为 `StrategyParallelWork`：

- 单个区域最大并行度默认为 `逻辑处理器数 - 1`，至少为 1；进程环境变量 `SENGOKU_MAX_PARALLELISM` 可调低上限，非正整数回退默认，上界裁剪到默认值，重启生效。没有设置 CPU 亲和性，不保证为操作系统保留一个处理器。
- 进程级非阻塞门控制并行区域：一个区域展开并行时，其他房间和嵌套区域顺序计算，不等待门锁。减少同时展开多套工作线程的争用，并保留结果顺序。
- 这不是整机 CPU 使用率上限；多个房间的请求线程仍可以同时工作。
- 并行度按 `min(配置上限, max(1, 项数 / 最小批量))` 决定，至少两批才展开。不再因为刚达到一批阈值，就给小任务申请整机并行预算。
- `MapOrdered` 按输入索引写结果，即使任务完成顺序不同，输出顺序仍完全一致。

## 已并行化

1. 全势力视野快照：每个势力独立计算；每工作线程最少 4 个势力，8 个势力起尝试并行，之后按势力 ID 写入台账。
2. AI 敌情感知：同一势力一天只扫描一次敌军与已知敌城；不同势力的感知并行计算，军事行动仍顺序提交。
3. 世界状态投影：势力、据点、单位、人物和地图人物至少达到各自最小批量的两倍才尝试并行映射，输出保持实体 ID 顺序。
4. 大地图地形/区域数组：每工作线程最少 4096 格，8192 格起尝试并行转换。
5. 人物长期目标：领地计数由逐人物重复扫描改为一次聚合，每工作线程最少 32 人，64 人起尝试并行刷新。
6. 高速观战：多日推进只在批次末生成一次完整状态，减少重复 DTO 构造、JSON 序列化和 HTTP 往返。

## 仍保持串行

- 日内系统链：不同 Order 存在明确因果依赖。
- 战斗伤亡、占领、商队撮合、税费、贡纳和实体增删：会写共享集合或影响后续系统。
- 玩家命令：单局宿主使用锁保证命令与日推进不交叉。

后续若要继续并行战斗，应先按参战单位建立冲突图，只让完全不共享参战者的战场并行计算，再顺序应用结果。经济系统也应先计算每城增量命令，而不是并行修改金粮。

## 验证

- 两次全势力 AI 各推进 365 日，最终世界存档 JSON 完全一致。
- 单次 365 日长稳测试验证日期、兵力、人口、粮食和金钱没有非法负值。
- `MapOrdered` 使用 10,000 项逆序输入验证并行映射不会改变顺序或遗漏结果。
- 新增嵌套计算、异常后恢复的回归测试；心跳未发现世界版本变化时，网页不再请求完整 DTO。
- 新增 4 个独立世界并发推进 31 天，与顺序世界比较完整存档（包含运行时台账），以及小批量留在调用线程的回归。
- 本轮新增小剧本基准，仍未建立大型剧本与不同硬件的性能基线，不能据此宣称普适加速倍数。
- 当前开发机识别 12 个逻辑处理器，调度上限为 11。

## 日志与等待开销

- 仿真不再为每个世界创建控制台日志器，而是复用应用的 `ILoggerFactory` 和过滤配置；独立创建的无配置仿真默认静默。高频逐步移动日志降为 Debug，正常 AP 不足不再按 Warning 输出。
- 日结诊断与 AI 缓冲选项传入仿真；开启日结文件时写入各自 `sessions/<会话标识>` 子目录，避免多房间混写。
- `GameLoopBase` 暂停采用异步信号，不占用线程池等待；并发启停受到生命周期锁保护，故障后也能清理再启动。战略房间本身仍由 ready 请求推进，并没有后台自动日结线程。

## 可复跑基准

在仓库根目录运行（独立工具，不在解决方案默认构建列表中）：

```powershell
dotnet run --project SengokuScroll.Benchmarks -c Release -- --rooms 1 --days 180 --degree 1
dotnet run --project SengokuScroll.Benchmarks -c Release --no-build -- --rooms 1 --days 180 --degree 11
dotnet run --project SengokuScroll.Benchmarks -c Release --no-build -- --rooms 4 --days 180 --degree 1
dotnet run --project SengokuScroll.Benchmarks -c Release --no-build -- --rooms 4 --days 180 --degree 11
```

工具固定 `mini_kanto` 和全 AI 模式，预热 5 日，预先创建世界，测量每日推进及 DTO 构建；不包含 HTTP、浏览器绘制、加载剧本、最终存档序列化。输出进程 CPU 时间、墙钟时间、吞吐、单世界日结 P50/P95、整个进程的累计分配量，以及各局完整存档 SHA-256。`--degree 1` 仅关闭局内展开，多个世界仍并发利用多个核心。比较不同进程输出的 hash 可核对预算变化是否影响结果。

这组样本说明小地图并行开满并无稳定收益，多房间本身已能使用多核。当前小剧本多房间部署可以先比较 `SENGOKU_MAX_PARALLELISM=1` 与默认预算，再决定配置；没有据此关闭大型场景的局内并行能力。该表不是正式的多次统计基准，也不是新增调度策略相对旧版的可靠加速比。
