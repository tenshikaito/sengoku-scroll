# 多核优化说明

## 原则

策略仿真采用“并行只读计算、固定顺序提交”。并行阶段不能写共享世界；涉及兵力、金粮、据点归属、战争分数和实体增删的结果必须按系统 Order、势力 ID、实体 ID 顺序提交。这样才能保证相同种子、相同命令得到相同存档。

统一调度入口为 `StrategyParallelWork`：

- 单个区域最大并行度为 `逻辑处理器数 - 1`，至少为 1；没有设置 CPU 亲和性，不保证为操作系统保留一个处理器。
- 进程级非阻塞门控制并行区域：一个区域展开并行时，其他房间和嵌套区域顺序计算，不等待门锁。减少同时展开多套工作线程的争用，并保留结果顺序。
- 这不是整机 CPU 使用率上限；多个房间的请求线程仍可以同时工作。
- 小集合低于阈值时自动顺序执行，避免线程调度成本大于收益。
- `MapOrdered` 按输入索引写结果，即使任务完成顺序不同，输出顺序仍完全一致。

## 已并行化

1. 全势力视野快照：每个势力独立计算；4 个势力起并行，之后按势力 ID 写入台账。
2. AI 敌情感知：同一势力一天只扫描一次敌军与已知敌城；不同势力的感知并行计算，军事行动仍顺序提交。
3. 世界状态投影：势力、据点、单位、人物和地图人物达到各自阈值后并行映射，输出保持实体 ID 顺序。
4. 大地图地形/区域数组：4096 格起并行转换。
5. 人物长期目标：领地计数由逐人物重复扫描改为一次聚合，人物任务达到 32 人起并行刷新。
6. 高速观战：多日推进只在批次末生成一次完整状态，减少重复 DTO 构造、JSON 序列化和 HTTP 往返。

## 仍保持串行

- 日内系统链：不同 Order 存在明确因果依赖。
- 战斗伤亡、占领、商队撮合、税费、贡纳和实体增删：会写共享集合或影响后续系统。
- 玩家命令：单局宿主使用锁保证命令与日推进不交叉。

后续若要继续并行战斗，应先按参战单位建立冲突图，只让完全不共享参战者的战场并行计算，再顺序应用结果。经济系统也应先计算每城增量命令，而不是并行修改金粮。

## 验证

- 两次全势力 AI 各推进 365 日，最终世界存档 JSON 完全一致。
- 单次 365 日长稳测试验证日期、兵力、人口、粮食和金钱没有非法负值。
- `MapOrdered` 使用 10,000 项逆序输入验证并行映射不会改变顺序或遗漏结果。
- 新增嵌套计算、异常后恢复的回归测试；心跳未发现世界版本变化时，网页不再请求完整 DTO。
- 本轮没有建立大型剧本与不同硬件的性能基线，不能据此宣称某个加速倍数；后续需分别测吞吐、P95 回合延迟和分配量。
- 当前开发机识别 12 个逻辑处理器，调度上限为 11。
