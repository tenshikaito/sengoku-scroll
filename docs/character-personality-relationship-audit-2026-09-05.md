# 人物性格与关系系统：设计、实现和缺口核对

后续状态：第一批基础问题已修复，见 [人物基础修复](character-foundation-2026-09-05.md)。本报告保留修复前审计证据。

审计基线：本地提交 `32e6bee`。本轮仅分析、隔离复现和编写报告，不修改游戏逻辑，不推送远端。

## 结论

**有明确的设计文档，但不是一份已经闭环的“人物社会系统规格书”。** 已定义十项性格、方向性私人关系、亲疏/信任、看法条目、亲属身份和忠诚；实际实现以战斗性格规则、人物信息展示、会面交谈/赠礼和存档为主。人物差异化配置、关系统一计算、社会 AI、事件驱动关系变化和忠诚行为尚未形成完整闭环。

这不是“什么都没做”，也不能称为“性格、关系系统已经完整上线”。

## 2. 性格系统

权威代码结构：`SengokuScroll.Domain/Definitions/CharacterDefinition.cs` 的 `PersonalityData`。

| 代码字段 | 当前用途 | 完成度判断 |
| --- | --- | --- |
| Temper 性情 | 战斗强袭相关组合阈值、DTO 展示 | 有局部行为接入 |
| Courage 勇气 | 强袭、主将行动、追击、劝降、守城、治理偏好 | 接入较多 |
| Principle 主义 | 治理内政倾向、展示 | 少量接入 |
| Action 行动/慎重 | 强袭、撤退、追击、主将行动、俘虏命运、治理 | 接入多，但概念方向有冲突 |
| Friendship 情义 | 亲属展示的亲疏档位计算 | 不等于对某人的好感，也不等于忠诚 |
| Ambition 野心 | 强袭、追击、劝降、主将行动、治理 | 有军事偏好，未发现完整夺权/叛变闭环 |
| Hobby 喜好 | DTO；前端拆分为五类数值 | 主要展示，五类不是独立后端属性 |
| Desire 物欲 | DTO/展示 | 未发现接入人物 Gift 收益或拒收判断 |
| Drinking 饮酒 | DTO/展示 | 未发现完整饮酒行为消费链 |
| Fortune 运势 | DTO/展示 | 未发现接入现有确定性战斗掷点的消费链 |

上述“未发现”指当前策略业务引用追踪，不宣称其他尚未开发模式永远不使用它们。

### 2.1 最重要的配置断点：人物性格全是默认值

`StrategyScenarioCharacterFactory.Create` 第 40 行直接赋 `DefaultPersonality()`；83–98 行把十项全部设为 50。`StrategyScenarioDocument.cs` 中 `StrategyCharacterDefinition` 332 行起没有 Personality 配置入口。

隔离运行结果：正常 `StrategySimulationHost.LoadScenario("mini_kanto")` 后，DTO 返回 **38 名人物，只有一种性格组合，十项均为 50**。直接剧本初始角色为 11 名，额外人物在完整主机初始化流程中出现，不能把 11 当成完整开局人数。

意义：战斗规则虽然支持胆勇/慎重/野心差异，当前标准开局并没有给它们差异化输入。人物能力、任务、位置等仍可能不同，不能说所有 AI 行为完全相同。

### 2.2 文档和代码方向不一致

- 共用设计：Action 0=谨慎、100=果断。
- 代码定义：Action 0=轻率、100=慎重；BattlePursuitRules、BattleRetreatRules 等按高值慎重使用。
- UnitDestructionRules 约 190 行又将其命名为 `aggressiveness`，高值降低对方逃脱概率。这未必是数值算法错误，但必须明确是“围捕严密”还是“更好战”，不可继续混用。
- StrongholdGovernanceEvaluator 约 146 行使用 `(100 - Action) / 18` 加内政偏好；是否符合“慎重”语义也需策划确认。

建议以现有多数战斗规则为基础，将其明确为 Caution/慎重；旧存档字段可暂留 `Action`，不要不经迁移直接翻转数值。

### 2.3 字段命名漂移

共用文档用 Personality.Loyalty、Preference、Materialism，代码为 Friendship、Hobby、Desire。尤其 Personality 的“情义”与 Character.Loyalty 的“对势力忠诚”必须分开。文档 Emotion 是 byte 0–100，实际 Character.Emotion 是 int，社交逻辑按 −100～100 限制，亦需统一。

### 2.4 喜好五分类是占位推导

`strategyCharacterPersonality.ts` 的 `hobbyCategoryValues` 用一个 Hobby 数值和人物 ID 拆出武具、书籍、艺术、舶来品、宝物偏好。此处已注释“待独立字段实装前”。不能向玩家宣称其为五项真实配置，更不能直接拿这组展示数值去算赠礼效果。

## 3. 关系系统实际有四层

1. **身份关系**：FatherId、MotherId、SpouseId、MasterId、EnemyIds 等。
2. **A→B 数值关系**：CharacterRelationship.Relationship、Trust，各 −100～100；反向是另一条记录。
3. **看法条目**：ViewEffects，支持原因、幅度、永久/长期/临时标签和到期日。
4. **对势力忠诚**：Character.Loyalty，基础值默认 50，可加 ActiveEffects；不是任意人物间的好感。

势力 Diplomacy 是另一系统。外交使节成功率读取势力间 Relationship，而不是人物 CharacterRelationship。私人亲密不应自动等于国家同盟。

### 3.1 已落地的玩法

`CharacterSocialActions.TryInteract` 支持 Talk/Gift：

- 只有玩家当主可作为 actor，不是文档概念表中的全员自主社交。
- 双方必须存活、非同一人、同地点；地点涵盖同据点、同地图格、同单位。
- Talk 消耗 1 AP；Gift 消耗 2 AP 和个人金钱 100，钱转给目标。
- 魅力影响增益；仇敌关系给予减益，但最终每次变化至少 +1。
- 双向关系与信任分别增加，数值钳制；双方心情增加。
- 主机和 API 已接通；现有 API 测试验证交谈扣 AP 并增加双向数值；完整 v2 存档保存运行时对象。

因此交谈/赠礼不是空按钮，但尚未体现物欲、礼物类型、个人喜好、拒绝、冷却或边际递减。

### 3.2 展示与实际关系脱节（已复现）

`CharacterRelationsHelper.ResolveRelationTone`：

- 任一方 EnemyIds 含对方就显示“仇视”。
- 亲属/师父亲疏来自双方 Personality.Friendship 平均值。
- 不读取 CharacterRelationship.Relationship 或 Trust，也不汇总 ViewEffects。

隔离实验人为安排同地并给予足够 AP，对仇敌连续交谈 200 次：成功 200 次，亲疏 **−80→100**、Trust **100**，展示仍为 **“仇视”**。这不是正常一天有 200 AP 的宣称，而是用于证明缺少冷却/递减和展示不同源的压力复现；真实游戏 AP 会限制单日次数。

此外，Relations 表只收亲属/师父/仇敌等身份关系，普通通过交谈结识的人并不会因为有数值关系就自然进入该表。反向师徒“弟子”、兄弟姐妹等也没有完整推导。

### 3.3 看法尚不是完整事件记忆系统

`IntelEntityBootstrapHelper` 仍直接写入“骏河继承之争”“杀害本家当主”“清洲威胁”等示例，使用固定目标 ID；不以实际发生该事件为必要条件。函数也没有按 scenarioId 明确限制为 mini_kanto。

前端 `strategyIntelSystemData.ts` 965–996 行：即使是实际世界，只要对应 viewEffects 为空，也可能回退 `PERSON_OUR_VIEW_EFFECTS` / `PERSON_THEIR_VIEW_EFFECTS`。空真实数据不应被解释成“请展示虚构关系原因”。

DTO 下发基础 Relationship/Trust 与独立 ViewEffects；未发现统一的“有效亲疏/有效信任”公式。文档本身写明 ViewEffects 主要用于展示与后续玩法，不能把显示 −100 看法等同于所有 AI 已按 −100 计算。

### 3.4 临时效果到期仍是预留

EntityEffect.ExpiresOn 能保存，但当前引用主要在序列化映射；`EffectDurationKind` 注释明确“日推进后到期移除（待 System 实装）”。`ResolveEffectiveLoyalty` 直接累计效果，没有按日期过滤。因此临时忠诚效果一旦被写入，不能假定会如期失效。

### 3.5 缺少的行为闭环

未发现通用链条：关系事件 → 有效亲疏/信任 → 忠诚/合作等决策 → 结果事件 → 再更新关系。

人物日常 AI 主要按体力、年龄、疾病、心情、行动计划和任务评估 Rest/Visit/TaskRun；Visit 主要是去据点，不等同于按关系选择朋友并交谈。当前私人亲疏和信任未普遍用于任命意愿、军令服从、援军选择、投奔、背叛、婚姻或外交使节接受。

RPG 随从招募、薪酬、叛逃是设计方向，不应作为本模式已经实现的功能。战场劝降存在，但不是同一个“家臣低忠诚叛变”机制。

## 4. 需要明确补写的设计决策

以下是本轮建议，不是朋友原文已经定稿的规则：

1. 固定性格维度的名称、方向、上下限、默认值，决定运势是否应独立于性格；为剧本提供 Personality 输入和校验。
2. 分开“重义倾向”“对某人的亲疏/信任”“对当前势力忠诚”；不要用一个数值包办。
3. 身份与亲疏分列：仇敌是历史身份还是当前状态？是否允许和解？亲属可以互恨、敌将也可互相敬重。
4. 统一有效关系计算和 UI 分档，让展示与实际消费同源；正反方向独立。
5. 明确事件类型及后果：救援、赏罚、失约、战死、杀亲、任命、赠礼；事件 ID、防重复、过期/衰减、永久记忆保留条件。
6. 社交确定冷却/递减、拒收和礼物匹配；财富影响不能简单洗掉永久仇恨。
7. 先接一两个可解释消费点，例如合作意愿/劝降，再逐步接叛变；不要用隐蔽随机数直接引爆高损失剧情。
8. 明确信息可见性：谁能看到敌人的性格、对第三人的信任与秘密怨恨？多人场景不能把完整关系图无条件当公共信息。
9. 明确规模边界：采用稀疏关系边，避免所有人物两两建关系；事件记忆按可审计生命周期压缩，避免重演行情历史的无限增长。

## 5. 建议实施顺序

**第一批：统一概念与修正真实性。** Action 定义、剧本性格输入、移除正式世界 mock 回退、关系显示同源、临时效果到期。

**第二批：社交闭环。** 关系有效值、正反方向、事件记忆、Talk/Gift 的冷却与偏好、事件与亲疏 UI 解释。

**第三批：人物自主行为。** 合作、拒绝、忠诚变化、继承立场；之后再设计叛变、婚姻、派系等高影响机制。

前三批都应补存档往返、多人视角隔离、事件幂等、确定性、长期内存边界的测试。
