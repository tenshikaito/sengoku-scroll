# 项目复审与修复记录 · 2026-09-05

## 范围与结论

后续增量修复与当前验证结果见 [第二轮复审](project-review-followup-2026-09-05.md)。本文保留上轮检查时的历史结论与测试数量。

以 `ee62458` 为起点检查项目结构、运行时代码中的非确定性/并发危险模式、应用循环、策略宿主与存档、组织/贸易关联、联机房间与权限、前端会话/请求/轮询、发布脚本和现有文档。对发现的高风险调用链深入追踪，并执行全套回归与发布产物 HTTP 冒烟验证。

这是一轮项目级静态审查和针对性验证，不表示每种玩法组合都经过人工试玩，也不能把测试全绿解释成游戏无缺陷。此前“联机完整落地”的表述过强：房间世界隔离已实现，但私人报告和贡纳台账仍有单机假设，见下方保留项。

## 已修复

| 范围 | 发现的问题 | 修复与验证 |
| --- | --- | --- |
| API 权限 | URL 尾斜杠可绕过基于字符串后缀的存档/加载限制 | 按已解析的动作名限制；覆盖两套路由与尾斜杠 |
| 联机情报 | 全局移动/AI/日结诊断可暴露敌方信息；可请求任意精确谍报 | 房间上下文禁用诊断和直接情报注入；6 个接口回归用例 |
| 指令去重 | 失败指令释放后旧队列节点残留，重试记录被过早淘汰 | 链表节点与字典共同删除；覆盖缓存填满、重试、淘汰 |
| 指令隔离 | 两个玩家使用相同命令号会相互冲突 | 去重键包含玩家 ID，仍限制每房间缓存总数 |
| 通知失败 | 日推进成功后通知失败可能释放去重记录，重试再次推进 | 提交成功先确认；通知独立超时与容错，轮询恢复已提交状态 |
| 房间关闭 | 最后一人退出后才删房，加入请求可能抢入；关闭信号量使排队请求异常 | 在门锁内移除并标记关闭；唤醒的请求不能使用已撤销身份 |
| 容量 | 多个创建请求可同时通过 64 房间上限检查 | 串行化创建容量检查和注册，既有房间继续独立执行 |
| 回合请求 | 迟到的准备请求可能应用到下一回合 | 必填 `expectedTurn`，不符返回 409；覆盖已推进后的旧请求 |
| AI 托管 | 真人集合为空时退回单机规则，默认势力不会被 AI 接管 | 显式区分“无联机配置”和“联机无人在线” |
| 连接 | 单个 SignalR 连接断开会把仍有活动连接的玩家下线 | 采用认证 HTTP 活动租约，模拟时钟测试到期与重连 |
| LAN 网页 | `crypto.randomUUID()` 在非安全 HTTP 上不可用 | 用 `getRandomValues` 生成 128-bit 指令 ID，新增无 randomUUID 环境回归 |
| 标签页 | `localStorage` 会让多个玩家标签页共享并覆盖身份 | 凭据迁移至 `sessionStorage`；旧凭据首次读取时迁移 |
| 重连 | 瞬断导致启动重连失败时直接清空凭据 | 只有明确 401/404 才丢弃；临时网络错误保留凭据并提示 |
| 退出 | 房间消失后退出接口 404，玩家无法结束本地会话 | 已失效的房间/身份视为完成退出，其他网络错误保留会话 |
| 前端并发 | 慢轮询可重叠，旧响应覆盖刚执行的命令或已退出的会话 | 单个在途轮询、会话代次、状态对象和加载状态复核 |
| 单机 Auto | 任意真实请求失败都可能切到 Mock，让非法指令看似成功或瞬断后换局 | 只允许尚未建立真实会话时的初次只读不可达请求回退；写操作、规则拒绝及既有会话断线直接报错 |
| 轮询成本 | 无变化的世界也反复映射和序列化完整 DTO | 认证轻量心跳续期，版本变化才拉状态；见实测数据 |
| 存档写入 | 直接覆盖文件，异常中断或并发写入会破坏旧档 | 每槽锁、同目录临时文件、刷盘、完整替换；80 次并发写读验证 |
| 存档读取 | `save:null` 可使槽位列表异常；恢复失败会替换掉原局 | 结构检查、保留旧仿真作用域，恢复失败回滚；非法存档回归 |
| 剧本路径 | 剧本名可携带绝对/相对路径 | 仅接受文件名，拒绝路径分隔符和非法文件名字符 |
| 组织与贸易 | 自定义组织 ID 使用进程随机化字符串散列，碰撞时合并不同组织 | 稳定散列、冲突探测、优先按名称/类别保留旧档 ID；同步商店判重及神社引用 |
| 应用循环 | `Start(isPause: true)` 反而打开暂停事件 | 正确设置初始暂停状态；验证恢复和停止后重启 |
| 多核 | 每个房间/嵌套区域都可展开一套接近整机的线程预算 | 非阻塞进程内并行区域门，争用时顺序计算；嵌套、异常恢复与全年确定性回归 |
| 发布 | 打包会强杀游戏，删除整个旧发行目录（含可能的存档），并删除开发 wwwroot | 每次新建发行目录，直接嵌入 dist；保留已有文件和运行中游戏；发布构建加入类型检查 |
| 部署说明 | Development 不托管静态页，却让开发玩家访问 5100 | 文档纠正为开发前端 5173、发行版 5100；生产无 WebRootPath 时安全回退 |

## 验证结果

- .NET 全量：424/424（Application 2、Strategy 388、Web API 34），新增 22 项回归。
- 修改通知超时后重新运行联机相关 18 项，通过；解决方案构建 0 警告、0 错误。
- 前端：5 项 Node 回归通过，TypeScript 检查和 Vite 生产构建通过。
- 策略测试包含相同种子两次各推进 365 日并比较最终存档，亦覆盖多核有序映射。
- 实际 `dotnet publish` 验证了从 dist 嵌入静态资源的路径；本次烟测包是依赖本机 .NET 的 Release 包，未完整执行 `build.cmd` 的 win-x64 自包含发布流程。
- 在本机 5116 端口启动 Production 包：首页及其 8 个静态资源 HTTP 200；创建/加入房间得到势力 1/2 的独立状态；第一人准备不推进、第二人准备推进一次；双方退出成功。测试进程已停止。
- 没有进行跨设备真人对局、后台标签页节流、长时间断网、完整浏览器点击流程或多节点压测。

## 轮询实测

同一 mini_kanto 房间推进一天后，本机回环 HTTP、PowerShell 客户端，各连续请求 20 次：

| 请求 | 单次响应体字节数 | 20 次总耗时 |
| --- | ---: | ---: |
| 完整 state | 134856 | 223.9 ms |
| heartbeat | 891 | 27.6 ms |

这是本机小剧本的一次样本，包含 HTTP 客户端开销，不是多核加速比，也不是大型地图的 P95 或容量承诺。直接收益是未变化时避免完整世界构造和传输。并行区域门控制的是线程展开，不能保证整机 CPU 使用率或保留某个硬件核心。
